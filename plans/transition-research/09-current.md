# Topic09 — Causal wine risks and faults

Approved direction connects features and risks to wine processes, and keeps physical faults distinct from structural evaluation ([design.md](../../docs/WorkingDocs/design.md#L13), [transition overview](../../docs/WorkingDocs/Winemaker04_to_05_Transition_Overview.md#L680)). The active contract assigns `Risks.ts` only `oxygenExposure`, `oxidation`, `rot`, and `greenCharacter`; `advanceRisks(lot, environment, days)` returns physical state, while `developLot` owns ordered daily steps and collected causes ([transition-contracts.md](../transition-contracts.md#L25), [field ownership](../transition-contracts.md#L63)). `PhysicalState` also contains fermentation and maturation fields, so risk advancement must preserve them and all origin, anchors, and source lineage ([wine/types.ts](../../src/game/wine/types.ts#L25)). `createHarvestLot` captures ripeness in green character and vineyard rot/noble rot in harvest state/anchors ([Anchors.ts](../../src/game/wine/Anchors.ts#L75)); `pressLot` adds oxygen exposure, oxidation, and green character ([Operations.ts](../../src/game/wine/Operations.ts#L210)). `WineFault` is a separate assessment output from axis fits ([evaluation/types.ts](../../src/game/evaluation/types.ts#L24)). The planned `Risks.ts` and `Development.ts` are not yet in source.

04's `C:/GitHub/winemaker04/src/lib/services/wine/features/featureService.ts` accumulates weekly risks and applies feature effects to stored characteristics/anchors; manifestation uses `Math.random()` (lines 399, 850, 1426-1430). `gameTick.ts:280` calls weekly risk processing alongside weekly fermentation tasks. Event triggers are called from `workcalculators/crushingWorkCalculator.ts:186` and `fermentationWorkCalculator.ts:146`. `constants/oxidation.ts` has state-dependent accumulation, while its pressing `riskModifiers` are not wired into the general event path ([transition overview](../../docs/WorkingDocs/Winemaker04_to_05_Transition_Overview.md#L371)). `greenFlavor.ts` configures harvest and crushing triggers; the observed event callers include crushing but no harvest call. `stuckFermentation.ts` evaluates setup risk and directly modifies perceived sweetness/body. `nobleRot.ts` and `greyRot.ts` process vineyard-stage accumulation; grey rot requires manifested noble rot and stops its evolution. These are scenario references, not 05 formulas. Since 05 `WineEnvironment` has no crop timing/ripeness fields, preserve the noble/grey trade-off in vineyard/harvest state rather than inventing it in cellar risk advancement.

**Proposed take:** Use deterministic bounded daily updates from current physical state and resolved environment, with named cause strings collected by `developLot`; do not add random feature rolls or a generic bonus engine. `diagnoseWine` should derive stuck fermentation only from active fermentation, sugar above the shared 4 g/L threshold, and insufficient yeast; physical fault thresholds stay separate from structural imbalance.

Critical scenarios: identical inputs replay identically and split-day advancement matches repeated one-day steps; oxygen/contamination pressure changes only owned fields and values remain bounded; unchanged harvest anchors/origin survive all risk steps; stuck diagnosis crosses each active-process, sugar, and yeast boundary; structural underfit alone never creates a physical fault; causes identify each environmental or state-driven change.
