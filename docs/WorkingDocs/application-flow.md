# Application Flow

Describe implemented 05 systems, state ownership, domain rules, and user interactions here, with links to their owning source. Distinguish implemented, partial, and deferred behavior. The [transition overview](Winemaker04_to_05_Transition_Overview.md) describes the design direction and the historical 04 reference; it does not establish 05 runtime behavior.

The browser connects the navigation prototype to the company authority. The available gameplay is creating or loading a company and advancing its calendar; wine production and the other game systems remain unimplemented.

## State owners and system boundaries

- [Game state and commands](../../src/game/core/) contain the company calendar and the `time.advance` command. [Calendar rules](../../src/game/calendar/Calendar.ts) validate explicitly supplied calendar lengths and dates; new companies use the trusted server configuration and its current defaults. [AdvanceTime](../../src/game/simulation/AdvanceTime.ts) calculates a new calendar state and a boundary event synchronously without modifying its input.
- [CompanySession](../../src/authority/session.ts) coordinates commands and committed snapshots using the [save-port contract](../../src/authority/contracts.ts). The [PostgreSQL candidate](../../src/server/postgres/PostgresCompanySavePort.ts) owns company snapshots, revisions, receipts and attempt recovery through transactions. Its connection and owner-scope binding belong to trusted server code.
- The [HTTP authority](../../src/server/api/server.ts) scopes requests by selected database player profile or the shared unassigned-company scope, then supplies the trusted company session. The optional [Supabase JWT verifier](../../src/server/api/auth.ts) is retained for future bearer-authenticated clients; the local player flow does not use it.
- [Browser client](../../src/client/) loads database-backed player profiles, lists profile-scoped companies, sends commands to the authority and retains uncertain command intents in browser storage. The Vite development proxy forwards `/api` to the local authority.
- Named player profiles are database records. The welcome screen lists profiles from the authority; creating or renaming a profile updates its database row. Selecting a profile sets its ID as the company owner, so the same profile can be selected from another browser. On a normal return the last selection is restored; when there is no saved selection and only one profile exists, it is selected automatically, as in 04. Logging out shows the selection screen. The screen also offers Create New User and a company-name form together; Start creates and opens an unassigned company without creating a profile. Cancel closes that form and Create Company Without User reopens it. Unassigned companies appear in the selection screen across browsers. Like 04, selectable profiles and unassigned companies have no password or private authentication boundary: anyone who can use the service can select them. Profile account linking and recovery are not implemented.
- The welcome screen reuses 04's vineyard image and displays placeholder leaderboard and getting-started content. README and version log open as text; the Trello item is a placeholder.
- [React presentation](../../src/App.tsx) owns temporary navigation, selection, panel, and dialog state. [Pixi scenes](../../src/scene/SceneCanvas.tsx) draw placeholders and translate pointer input into presentation intents. They do not run simulation or write saves.

## Actions and interactions

- The prototype opens at Estate. The user can navigate Estate, Winery, Cellar, Company and the Management panels, select placeholder scene features through the scene or its list, open and close details and the wine dialog, and toggle the Activity Manager. Once a company is loaded, its committed calendar appears in the top bar and Advance Time submits a command. Navigation and panel state are not saved.
- The server supports player-profile listing/creation/renaming and company creation, loading, command dispatch and uncertain-command resolution. Company creation uses server-owned calendar configuration, not values supplied by the client. A successful `time.advance` command advances one configured week, reports season/year boundaries, and is published only after the candidate commit. The [relationship map](VariableRelationshipMap.md) describes the currently implemented calendar dependency.

## Rules, partial systems, and deferred work

- The implemented tick only advances the calendar. Weather, vineyard growth, staff work, wine development and evaluation, finance, progression, the shared market and other gameplay are not implemented. No daily wine substeps or wine formulas are implied.
- The database records pending attempts once reserved and can resolve them from another process. A confirmed `not-committed` resolution durably fences the whole command ID and any matching reservation, so a delayed delivery of that intent cannot later commit. A new player decision uses a new command ID. A competing reservation with a different payload is not canceled.
- A request lost before any reservation is durable cannot be discovered from storage alone: the original client retains its command ID and payload and retries that intent until the outcome is known. Another device cannot see an intent that has not reached durable storage. Revisions and receipts prevent stale overwrites and duplicate commits; they do not replace client-side recovery.
- The browser stores an intent before sending and uses the Web Locks API to coordinate commands, recovery and company switching across same-origin tabs. It blocks another command and company switching while a known intent is unresolved. After a command or recovery it reloads the company; if that reload fails, advancing stays disabled until a successful refresh. A cross-tab settlement also requires a refresh. Local storage and Web Locks must be available. A different device can resolve a server-known reservation; if the server has no record, only the original browser can retry its retained intent.
- Production hosting must provide its own same-origin `/api` routing, TLS and operations. The configured Supabase pooler was tested previously with certificate verification using the supplied root CA. The current private schema must be recreated to add player profiles; this task did not apply it remotely. The earlier isolated database test used a synthetic identity; a full profile/company browser flow against the configured remote project has not been verified in this work. Supabase anonymous sign-in is not used for local player profiles.
